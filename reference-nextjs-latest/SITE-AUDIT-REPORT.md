# Nahian Fashion — সাইট অডিট রিপোর্ট

তারিখ: ১০ জুন ২০২৬ | অডিট স্কোপ: পুরো কোডবেস + লাইভ সাইট (nahianfashion.com) + GTM কনটেইনার

---

## সারাংশ

সাইটের সিকিউরিটি ফাউন্ডেশন ভালো (অ্যাডমিন অথ, প্রাইস ভেরিফিকেশন, CSP, env ফাইল গিটে নেই, TypeScript এরর-মুক্ত)। **কিন্তু একটা ক্রিটিক্যাল বাগ আছে যেটা খুব সম্ভবত ফেসবুক অ্যাড থেকে অর্ডার না আসার মূল কারণ** — অর্ডার API-র IP-ভিত্তিক rate limit। এটা ফিক্স না করে অ্যাড চালানো উচিত না।

## 🔴 সমস্যা #১ (ক্রিটিক্যাল): অর্ডার API-তে ঘণ্টায় ৫টা অর্ডারের IP লিমিট — ফেসবুক অ্যাডের অর্ডার ব্লক হওয়ার সবচেয়ে সম্ভাব্য কারণ

**ফাইল:** `src/app/api/orders/create/route.ts` (লাইন ৯–১৯)

```ts
// 5 orders per hour per IP
if (!checkRateLimit(`order:${ip}`, 5, 60 * 60 * 1000).allowed) {
  return NextResponse.json({ error: 'Too many orders created from this IP...' }, { status: 429 });
}
```

**কেন এটা ফেসবুক অ্যাডের ক্ষেত্রে মারাত্মক:**

1. **বাংলাদেশের মোবাইল অপারেটররা (GP, Robi, Banglalink, Airtel) CGNAT ব্যবহার করে** — হাজার হাজার গ্রাহক একই পাবলিক IP শেয়ার করে। ফেসবুক অ্যাডের ট্র্যাফিক প্রায় ১০০% মোবাইল ডেটা থেকে আসে। ফলে এক ঘণ্টায় একই অপারেটর-IP থেকে ৫টা অর্ডার-চেষ্টার পর বাকি **সব আসল কাস্টমার 429 এরর পায়** এবং স্ক্রিনে ইংরেজিতে `alert("Order failed: Too many orders created from this IP...")` দেখে চলে যায়।

2. **কাউন্টার ভ্যালিডেশনের আগেই বাড়ে** — ব্যর্থ/অসম্পূর্ণ রিকোয়েস্ট, বট, রিট্রাই — সবই ৫-এর কোটা খেয়ে ফেলে। কাস্টমার একবার এরর পেয়ে আবার "Place Order" চাপলে সেটাও কোটা খরচ করে।

3. **সবচেয়ে খারাপ সম্ভাবনা:** যদি আপনার reverse proxy (nginx) `X-Forwarded-For` হেডার ফরোয়ার্ড না করে, তাহলে সব ভিজিটরের IP = `'unknown'` হিসেবে গণ্য হয় → **পুরো সাইটে ঘণ্টায় সর্বোচ্চ ৫টা অর্ডার!** Docker-এর ভেতরে অ্যাপ চলায় এটা যাচাই করা জরুরি।

4. **আপনি নিজে টেস্ট করলে কাজ করে কেন:** আপনার নিজের ব্রডব্যান্ড IP ইউনিক, তাই আপনি কখনো লিমিটে পড়েন না। এটা আপনার পর্যবেক্ষণের সাথে হুবহু মিলে যায়।

**কীভাবে নিশ্চিত হবেন (সার্ভারে):**
```bash
# nginx access log-এ 429 খুঁজুন
grep ' 429 ' /var/log/nginx/access.log | grep '/api/orders/create' | wc -l
# অথবা nginx config-এ X-Forwarded-For সেট করা আছে কি না দেখুন
grep -r "X-Forwarded-For" /etc/nginx/
```

**ফিক্স (যেকোনো একটা বা কম্বিনেশন):**
- লিমিট অনেক বাড়ান: প্রতি IP ঘণ্টায় ৫ → অন্তত ৩০–৫০।
- IP-র বদলে **ফোন নম্বর-ভিত্তিক** rate limit করুন (`order:${normalizedPhone}`) — স্প্যাম ঠেকাতে এটাই বেশি কার্যকর, CGNAT সমস্যাও নেই।
- `ip === 'unknown'` হলে rate limit **skip** করুন (এখন উল্টোটা হচ্ছে — সবাই এক বাকেটে পড়ছে)।
- কাউন্টার শুধু **সফল অর্ডারের পরে** বাড়ান, রিকোয়েস্টের শুরুতে না।
- nginx-এ নিশ্চিত করুন: `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`

## ফেসবুক অ্যাড ট্র্যাকিং — যা পরীক্ষা করেছি

✅ **যা ঠিক আছে:**
- GTM (`GTM-WBQH8573`) সব পেজে লোড হয় (`src/app/layout.tsx`)।
- লাইভ GTM কনটেইনার যাচাই করেছি — তাতে Facebook Pixel আছে এবং `PageView`, `ViewContent`, `AddToCart`, `Purchase` ইভেন্ট ম্যাপ করা।
- thank-you পেজে GA4-স্টাইল `purchase` ইভেন্ট dataLayer-এ পুশ হয় (transaction_id, value, items সহ)।
- CSP-তে `connect.facebook.net` ও `www.facebook.com` অনুমোদিত — পিক্সেল ব্লক হয় না।
- লাইভ অর্ডার API সচল (প্রোব করে 400 ভ্যালিডেশন রেসপন্স পেয়েছি, সার্ভার ডাউন না)।

⚠️ **দুর্বলতা (অ্যাড পারফরম্যান্সে প্রভাব ফেলে):**
1. **`InitiateCheckout`/`begin_checkout` ইভেন্ট নেই** — checkout পেজে কোনো dataLayer পুশ হয় না। ফলে ফানেলের কোন ধাপে কাস্টমার ঝরে যাচ্ছে সেটা Ads Manager-এ দেখা যায় না। সমস্যা #১-এর মতো বাগ ধরাও কঠিন হয়ে যায়।
2. **Purchase ইভেন্ট শুধু ক্লায়েন্ট-সাইডে** thank-you পেজে fire হয় — কাস্টমার পেজ লোড শেষ হওয়ার আগে বন্ধ করলে বা অর্ডার-fetch ব্যর্থ হলে কনভার্সন হারিয়ে যায়। **Meta Conversions API (server-side)** যোগ করা উচিত — iOS 14+ ও অ্যাড-ব্লকার ইউজারদের কনভার্সনও তাহলে ট্র্যাক হবে। অর্ডার তৈরির API-তেই সার্ভার থেকে ইভেন্ট পাঠানো যায়।
3. Purchase কম রিপোর্ট হলে ফেসবুকের অ্যালগরিদম ভুল অডিয়েন্সে অপ্টিমাইজ করে — অর্থাৎ সমস্যা #১ ঠিক করলে ট্র্যাকিংও আপনা-আপনি ভালো ফল দেখাবে।

## 🔴 অন্যান্য হাই-প্রায়োরিটি সমস্যা

### #২: `prisma db push --accept-data-loss` প্রতি কনটেইনার স্টার্টে চলে
**ফাইল:** `entrypoint.sh` (লাইন ২৭)
স্কিমা আর ডাটাবেসে অমিল থাকলে এই ফ্ল্যাগ **কলাম/ডেটা মুছে ফেলতে পারে** — কোনো সতর্কতা ছাড়াই, প্রতিবার ডিপ্লয়ে। প্রোডাকশনে `prisma migrate deploy` (মাইগ্রেশন ফাইলসহ) ব্যবহার করুন, অন্তত `--accept-data-loss` সরিয়ে দিন।

### #৩: ভুল ক্যাটাগরির প্রোডাক্ট নীরবে প্রথম ক্যাটাগরিতে চলে যায়
**ফাইল:** `entrypoint.sh` (লাইন ৬৮–৮৭)
কমেন্টে লেখা "closest active category by name similarity" কিন্তু কোড আসলে `categories[0]` (যেকোনো প্রথম ক্যাটাগরি) assign করে। ক্যাটাগরি rename করলে প্রোডাক্ট ভুল জায়গায় দেখাবে, কেউ টেরও পাবে না।

### #৪: স্টক-আউট সাইজও অর্ডার করা যায়, কোনো ইনভেন্টরি নেই
- checkout পেজে "Stock Out" ব্যাজ দেখায় কিন্তু বাটন disable হয় না (`src/app/(site)/checkout/page.tsx` লাইন ৫৮৮–৫৯৭, শুধু opacity কমে)।
- `api/orders/create` সার্ভারেও availability চেক করে না।
- অর্ডার হলে স্টক কমে না — ক্লায়েন্টকে ম্যানুয়ালি মেলাতে হবে।

### #৫: পেমেন্ট ভেরিফিকেশন ছাড়াই অর্ডার "paid" হয়ে যায়
**ফাইল:** `src/app/api/orders/create/route.ts` (লাইন ১৬৫)
```ts
amount_paid: paymentMethod !== 'cash' ? total : 0,
```
API `bkash`/`nagad`/`card` গ্রহণ করে এবং কোনো পেমেন্ট যাচাই ছাড়াই `amount_paid = total` সেট করে। সাইট থেকে শুধু `cash` পাঠানো হয়, কিন্তু কেউ সরাসরি API hit করে "টাকা পরিশোধিত" অর্ডার বানাতে পারে — ক্লায়েন্ট ভাববে টাকা পেয়েছে। যতদিন অনলাইন পেমেন্ট নেই, ততদিন `cash` ছাড়া বাকিগুলো allow-list থেকে বাদ দিন বা `amount_paid` সবসময় `0` রাখুন।

## 🟢 ছোটখাটো / পরে করলেও চলে

- `X-XSS-Protection` হেডার deprecated — সরিয়ে দিলেই হয়।
- `script-src 'unsafe-inline'` GTM-এর জন্য রাখা হয়েছে — nonce-ভিত্তিক করা গেলে ভালো।
- অর্ডার আইডি `NF-` + ৩২ অক্ষরের hex — ফোনে কাস্টমারকে বলতে অসুবিধা; ছোট (৮–১০ অক্ষর) random ID-ই যথেষ্ট।
- checkout/কার্ট কোডে প্রচুর `any` টাইপ — বাগ লুকানোর জায়গা।
- রুট layout-এ `force-dynamic` + প্রতি রিকোয়েস্টে DB query (site settings) — TTFB একটু বাড়ায়।
